Phase 7 · Executive Summary

What OMG actually is today

A direct answer, before the supporting evidence.

OMG is a Governance Intelligence & Continuity Layer — a genuinely deep, internally consistent system of record and advisory reasoning engine for AI governance decisions. It captures governance state, evidence, decisions, findings, and continuity signals across ~106 routed pages spanning 8 governance domains, and reasons over that data with real (not decorative) rule engines. It is not a runtime enforcement engine, not an execution control plane, and not yet an enterprise-hardened product — authentication always succeeds with no password, RBAC trusts a client-asserted role header by its own author's admission, there is no multi-tenancy, and no integration surface exists to any external system. OMG's greatest strength and its most serious gap sit side by side: an unusually disciplined "advisory-only, human-accountable" architecture, built on top of enterprise-readiness foundations (auth, notifications, export, configuration, integration) that are thin or absent.

Where OMG is genuinely strong

Governance Continuity, Reassessment taxonomy, Governance Journey Explorer, Decision Reconstruction, Governance Story, Governance Value metrics, Evidence/Findings/Corrective Actions/Certification lifecycle management, the Governance Reasoning Engine and its Human Decision Layer, Governance Studio, the Policy Engine, and a genuine dual-mode (localStorage / Postgres+NestJS) data architecture. These are real, evidenced, and consistently built to the same "advisory only, human-accountable" standard.

Where OMG is not yet enterprise-ready

Authentication (no password, always succeeds), backend authorization (trusts an unverified client header), multi-tenancy (none found), integrations (zero SSO/webhooks/third-party APIs), notifications (no delivery mechanism at all), export (one JSON button, four browser-print dialogs), configuration management (the settings page was removed and nothing replaced it), and deployment automation (no CI/CD, no IaC).

Phase 3 · Common vs. Configurable vs. ODF vs. Customer Runtime

Where each capability belongs

Only verified, real capabilities are listed in Sections A and B. Sections C and D are judgment calls about where future work should be delivered, argued from what exists today.

A Common OMG Platform — every customer gets this as standard

Industry-agnostic, reusable, already implemented.

Governance Continuity (reauthorization status) · Reassessment taxonomy + auto state-flip · Governance Journey Explorer, Decision Reconstruction, Governance Story, Governance Value metrics · Evidence Registry, Findings, Corrective Actions, Certification issue/renew/revoke workflow · Governance Readiness (6-function suite, per-asset and portfolio-wide) · Executive Dashboards (display composition) · Governance Reasoning Engine (conditions → violations → outcome ladder → recommended actions) and its Human Decision Layer (Accept/Reject/Defer) · Governance Studio (enable/disable + CRUD on rules, policies, action rules) · Policy Engine (authoring + auto-detected violations) · RBAC allow-list/action-key mechanism · Dual-mode data architecture with migration utility · Kill Switch mechanism (human-gated, audited) · Local Audit Trail.

B Configurable OMG Platform — customers configure without custom development

Verified real today — not proposed.

Governance Studio: enable/disable individual conditions, outcomes, and action rules; author and edit Policies and Policy Mappings; Compliance Pack Builder (Regulatory Source → Requirement → Obligation → Control → Policy); activate a Customer Governance Profile. This is the entire set of genuinely-configurable-today capabilities — thresholds such as reauthorization windows, evidence minimums, and mandatory authority fields are currently hardcoded constants, not configurable, and therefore do not belong in this section (see Phase 6 for the proposal to change that).

C ODF Customization — best delivered through services

Customer-specific governance workflows beyond Governance Studio's fixed catalogue · Industry-specific governance process content authored into the existing Policy/Compliance Pack structures · Organization-specific multi-step approval chains (OMG records a single decision point today, not a configurable chain) · Regulatory interpretation — mapping a customer's specific obligations into OMG's generic Requirement→Obligation→Control chain · Custom executive dashboards beyond the existing set · Integrating a customer's real identity provider (SSO/SAML/OAuth) since OMG has no such capability to configure · Multi-tenant environment setup for a specific enterprise deployment · Wiring notification delivery (email/Slack/Teams) to a customer's own tools, since OMG has no delivery mechanism to configure.

D Customer Runtime Governance Layer — should NOT be OMG core

Runtime enforcement engines — conflicts directly with OMG's deliberate advisory-only, human-accountable architecture; building one would require an entirely different execution-control system. Agent execution control planes — infrastructure/orchestration territory; zero code today touches a running agent process. Runtime policy engines — OMG's Policy Engine evaluates recorded/seeded state, never live traffic; a runtime version intercepts execution, a fundamentally different system. Tool execution brokers — OMG tracks tool grants (who is allowed what); it has no code that brokers an actual tool call. Enterprise orchestration controls — outside OMG's data-model scope; would require deep integration with a customer's own agent framework. Customer-specific kill-switch architectures — OMG's kill switch flips a status field it owns; it cannot and does not stop a running process anywhere. A true runtime kill switch requires integration with the customer's execution environment. Enterprise runtime gateways — no runtime traffic ever flows through OMG; it is a system of record, not a proxy.

Cross-Reference · Runtime Governability Analysis

The question underneath this entire review

Condensed from the dedicated Runtime Governability Discussion Paper prepared for Szilvia Földesné Ambrus's challenge; restated here because it frames the Kari Hyötylä findings below.

"Evidence may persist. Authority may still exist. But when context changes, the admissibility of continued execution should not necessarily persist by inheritance." — the challenge this entire analysis is grounded against.

OMG has essentially all the raw signal a runtime governability judgment would need — evidence, authority, certification, health, drift, reauthorization-by-date — already computed live, and already following the right architectural conventions (pure functions, computed not stored, advisory not blocking). What is missing is not new governance domains or new data. It is one composition layer that diffs "conditions now" against "conditions when authority was granted," and turns presence-checks into sufficiency-checks. Of the ten specific admissibility questions examined in the Discussion Paper, OMG answers one fully (reauthorization timing), four partially, and five not at all — every gap traces to a missing composition, not missing data. This finding is the basis for the entire Phase 6 evolution plan below.

Key Risks

What would actually hurt, in priority order

Critical

Authentication fails open

Login accepts any seeded email with no password and cannot fail. If this codebase were exposed beyond a trusted demo environment as-is, anyone could assume any role, including Super Admin.

Critical

Backend RBAC trusts a forgeable header

roles.guard.ts checks x-user-role with no cryptographic verification — its own author documents this. Combined with the authentication gap, the two together mean the backend has no real access control today.

High

No multi-tenancy

Cannot safely host more than one customer's data in a single deployment without building tenant isolation first.

High

Audit trail and user records are local-only in production

The backend AuditLog table has a GET endpoint but no POST — the frontend's ~60 audit call sites never reach Neon. This undermines exactly the auditability enterprise buyers will diligence hardest.

Medium

No CI/CD or infrastructure-as-code

Deployment topology is inferred only from hardcoded URLs in application code — there is no pipeline or IaC defining or automating it, risking configuration drift.

Medium

Two parallel readiness-scoring systems

readinessFoundation.ts (tiered) and governanceReadinessScore.ts (numeric) coexist with overlapping names — a maintainability and practitioner-communication risk, not a functional defect.

Medium

Zero integration surface

OMG cannot observe or connect to anything outside itself, which caps its practical governance value for real running AI systems until a Governance-to-Runtime interface exists.

Strategic Recommendations

In priority order, deliberately short

1

Fix authentication before any customer-facing production exposure

Not a "nice to have" — a blocking gap given the two Critical risks above.

2

Build the Governability Status composite

Context Drift + Evidence Sufficiency + Authority Currency + Admissibility signals, composed the same way getGovernanceStory() already composes existing data. Highest-leverage, lowest-cost addition available.

3

Introduce a configuration layer for hardcoded thresholds

Reauthorization windows, evidence minimums, mandatory authority fields — currently hardcoded constants, blocking any real per-customer configurability claim.

4

Define a Governance-to-Runtime event-ingestion contract

Lets customers and ODF wire in real signals without OMG ever becoming a runtime platform itself.

5

Resolve multi-tenancy and backend audit/user persistence gaps

Both are prerequisites before any multi-customer commercial deployment — not optional polish.

6

Do not build runtime enforcement, execution control, or agent orchestration into OMG core

Preserve the advisory/human-accountable boundary — it is OMG's most distinctive and defensible architectural property, confirmed consistent across every engine reviewed in this and prior sessions.

This assessment is evidence-only: every classification above traces to a specific file and line in the OMG codebase, verified by direct reading and exhaustive search, not inference from naming or intent. No code was modified in the course of this review.
