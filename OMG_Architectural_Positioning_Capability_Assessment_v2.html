Official OMG Positioning

OMG (OrchestrAI Model Governance) is intentionally positioned as a Governance Intelligence & Governance Operations Platform.

It is not intended to replace IAM platforms, runtime control planes, AI gateways, workflow engines, SIEMs, security platforms, execution platforms, or enterprise orchestration platforms.

OMG establishes governance state, evidence, ownership, accountability, reassessment, traceability, governance continuity, and governance intelligence.

Customer-specific runtime enforcement, identity integration, execution controls, operating-model implementation, workflow integration, and enterprise deployment patterns are intentionally delivered through configuration and ODF-based extensions according to organizational requirements.

Correction made in this refresh: the baseline report listed "multi-tenancy" as a category entirely excluded from OMG's scope. That is no longer accurate. OMG now has real EnvironmentRecord/TenantRecord/Workspace entities, a dedicated Workspace Login, and genuine data-tagging isolation (workspaceId/tenantId/environmentId fields) for the customer-evaluation surface. This is still not enterprise-grade multi-tenant SaaS infrastructure — there is no per-tenant hosting, no resource-quota isolation, and isolation is deliberately not retrofitted across OMG's ~110 shared governance pages (see Q5/Scope Matrix below) — but the "explicitly excluded" framing is retired in favor of "genuine, bounded workspace-level isolation."

Executive Summary

Meaningful ground was covered since the baseline — re-verified, not assumed

Since the 11 September baseline, four of the seven previously-identified Core gaps were actually closed in code: Evidence Sufficiency, Authority Currency, a composite Governability verdict, and Admissibility Assessment are all now real, computed engines (evidenceSufficiencyEngine.ts, authorityCurrencyEngine.ts, admissibilityEngine.ts, governabilityEngine.ts), and the previously-unreachable Reassessment Trigger entry point is now a working "File Reassessment Trigger" button on the Governability Dashboard. Separately, OMG gained a genuine (if bounded) customer-workspace isolation model — Environment, Tenant, and Workspace records with real data-tagging — which corrects the baseline's blanket "no multi-tenancy" claim. This re-verification also surfaced two things the baseline could not have known: OMG now runs two independent, non-unified models of "change" side by side, and its richest approval-chain capability is not reachable from the new customer-facing Workspace surface at all. Both are named plainly below, not smoothed over.

Direct Comparison

What changed since the 11 September baseline

Every item below is a reclassification driven by a specific, named code change — not a re-reading of the same evidence.

Resolved — baseline gaps that are now real, working capabilities

1 · Evidence Sufficiency

Baseline gap: presence-only check (assetEvidence.length > 0). Now: computeEvidenceSufficiency() (config/evidenceSufficiencyEngine.ts:33) scores availability, recency, completeness, relevance, and context-alignment into a real Sufficient / Partially Sufficient / Insufficient verdict, risk-tiered via DEFAULT_EVIDENCE_COMPLETENESS_MINIMUMS.

2 · Authority Currency

Baseline gap: authorityProfileCompleteness() never re-derived currency. Now: computeAuthorityCurrency() (config/authorityCurrencyEngine.ts:22) — whose own header comment states it "strengthens authorityProfileCompleteness()" — derives Current / Review Required / Expired / Not Applicable from lastReviewDate against fixed 90/60-day windows.

3 · Governability Status (composite verdict)

Baseline gap: health score, gates, drift, and continuity computed independently with nothing composing them. Now: computeGovernability() (config/governabilityEngine.ts:26) composes Evidence Sufficiency + Authority Currency + Admissibility into one live Governable / Governable With Conditions / Review Required / Governance Attention Required / Not Governable verdict, surfaced on GovernabilityDashboardPage.tsx and WorkspaceDashboardPage.tsx.

4 · Admissibility Assessment

Baseline gap: no mechanism diffed decision-time conditions against current conditions. Now: computeAdmissibility() (config/admissibilityEngine.ts:25) takes governance state, evidence sufficiency, authority currency, and an open-reassessment-trigger signal, and returns Continue / Continue With Conditions / Escalate / Reauthorize / Pause.

5 · Dynamic Reassessment Triggering entry point

Baseline gap: the taxonomy and consequence logic worked, but no reachable page could file a new trigger. Now: GovernabilityDashboardPage.tsx:63,173-178 has a working "File Reassessment Trigger" button, gated by canPerform('reassessmentTrigger:create'), calling saveReassessmentTrigger().

New — issues this refresh surfaced that the baseline could not have seen

N1Two disconnected "change" models now coexist

The simple ReassessmentTrigger model that feeds the new Governability Engine (types/index.ts:361-375) and a separate, richer ChangeRequest/approval-chain model (types/changeManagement.ts:102-133, its own services/changeManagementService.ts) declare two independently-named, incompatible GovernanceState enums (types/index.ts:330-338 vs. types/changeManagement.ts:137-147). getCurrentGovernanceState() (changeManagementService.ts:411) never writes back to the real AIAsset.governanceState field the Governability Engine reads.

N2The richer approval-chain module is unreachable from the Workspace surface

ChangeRequest.approvals?: ChangeApproval[] is OMG's only genuine multi-step, per-role approval sequence in the codebase — yet changeManagementService.ts has zero workspaceId/tenantId/environmentId scoping anywhere, and WorkspaceDashboardPage.tsx contains zero references to it. A customer evaluating OMG through the new Workspace Login can never see this capability.

1Two Disconnected Change Models

3Governance Configuration Change Authorization

Persists from baseline, now evidenced twice over: both Governance Studio and the new Governability Studio log configuration changes to the audit trail but require no approval before taking effect.

4Governance Signal Intelligence

Persists from baseline, partially improved. The new Governability Engine composes exactly three named signals (evidence, authority, material change) into one verdict — real progress — but broader correlation across findings, drift, and policy violations together still goes only as far as the Drift engine's own applyCompoundEscalation() rule (governanceDriftEngine.ts:109).

5Governance Record Portability

Persists from baseline, meaningfully improved (JSON/CSV/Print export now audited), but still scoped to one workspace at a time rather than a full platform-wide governance record export.

6Workspace Isolation Coverage

New observation, not necessarily a defect: the new isolation model is deliberately scoped to the Workspace Login → Workspace Dashboard surface only, and is not retrofitted across OMG's ~110 pre-existing shared governance pages. Worth stating plainly wherever "workspace isolation" is described externally.

Explicitly not listed as OMG gaps — because each belongs to a category OMG does not claim to be: IAM, SSO, Entra ID, Runtime Enforcement, AI Gateway, SIEM, Workflow Engine, Control Plane, Agent Runtime, and enterprise-grade multi-tenant hosting infrastructure specifically (narrowed from "multi-tenancy" broadly, per the correction above). Their absence from OMG core is correct architecture, not an oversight.

Final Executive Conclusion

The honest verdict, re-run

OMG is still best understood as a Governance Intelligence & Governance Operations Platform — and it closed real ground on that exact mission since the baseline: evidence sufficiency, authority currency, admissibility, and a composite governability verdict all moved from "future candidate" to "built and computed."

It also picked up a genuine, if deliberately bounded, workspace-isolation capability that the baseline was correct to not yet claim, and that this refresh was correct to stop calling "explicitly excluded."

The next evolution is not becoming a runtime platform or a general-purpose multi-tenant SaaS — it is reconciling the two change models that now run in parallel, extending the richest approval-chain capability to the surface customers actually see, and continuing to strengthen governability intelligence and record portability, all inside the mission OMG already claims.

Every classification in this refresh follows the same rule as the baseline: an item is only called an OMG gap after first determining it belongs to OMG Core — not to configuration, ODF implementation, customer environment, or a category explicitly outside OMG's stated scope. This refresh re-verified every classification against the current codebase directly; nothing here is carried forward unexamined. No code was modified in the course of this review.
