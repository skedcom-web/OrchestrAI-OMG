1 · Executive Summary

The governance-context half is built. The workflow half is split in two.

Javier's proposal needs OMG to supply a governed Approved Agent, organizational context, evidence, and authority state — and to receive back a consequential action outcome for re-absorption into governance.

OMG's actual current-state capability splits down the middle:

  • Governance context — asset registry, ownership, evidence, authority profile, audit trail, and a genuine computed decision-boundary via the Governability/Admissibility engines — is substantially built and wired, evidenced by working code, not aspiration.
  • Workflow / material-change exists too, but as two separate, non-interoperable implementations of "change" — one feeding the Governability Engine, one feeding a richer Change Request/Approval module — that do not talk to each other, and neither is reachable from the customer-isolated Workspace surface.
  • Consequential Action has no entity anywhere in the codebase. There is no field to hold "evidence returned from an external decisioning system." The literal string "Aegis" appears zero times in the repository.
Bottom line: OMG does not need new features to attempt Javier's bounded evaluation once. It needs a small, explicit, manually-supplied information package, entered into existing general-purpose fields (evidence records, reassessment triggers, audit entries) — because no field exists that was purpose-built to hold Aegis's output. This is a data-collection gap, not an architecture-development gap, with one caveat on workspace isolation (Phase F).

6 · Phase E

Required vs Optional Information

The smallest possible package that minimizes Javier's burden while maximizing evaluation quality.

Required

  • Chosen Approved Agent's asset ID — use an existing one (ast-101 is present in both the asset registry and change-seed dataset)
  • A mapped material-change category plus free-text description of the actual delivery change
  • Aegis's resulting decision/reasoning, as free text
  • An actor name/role and a timestamp for attribution

Nice-to-Have

  • Evidence artifacts beyond the minimum — improves fidelity, but the engine reports "Insufficient" rather than failing on sparse evidence
  • A populated GovernanceAuthorityProfile — if absent, the result simply reports authorityExists: false, itself an informative, valid result
  • Workspace/tenant scoping — only if the evaluation must run inside the isolated Workspace surface

Not Required

  • A new asset — OMG's own seed data already contains a usable Approved Agent
  • Any RBAC/persona configuration — 8 roles and a full action matrix already exist
  • Integration credentials, API contracts, or callback endpoints with Aegis — none of that machinery exists, so none of it can be configured
  • A new "Consequential Action" data model — building one would violate the "no new features" constraint of this exercise

8 · Phase G

ODF Execution Path

Using only what exists today, if Javier supplies the required information.

  1. Asset selection — /assets (AI Asset Registry) surfaces ast-101 as the Approved Agent; no new record created.
  2. Material change capture — a ReassessmentTrigger record is created, with triggerType mapped to the closest existing enum value and the delivery narrative placed in .comments.
  3. Evidence attachment — one or more EvidenceRecords are created and linked to ast-101 via assetId.
  4. Governability computation — computeGovernability() runs automatically, surfacing a GovernabilityResult on the Governability Dashboard — the decision boundary, visible before Aegis ever runs.
  5. Aegis reasoning — occurs entirely outside OMG; no code path exists for this step.
  6. Return of Aegis's output — recorded manually as a new EvidenceRecord (or AuditLog/WorkspaceAuditEntry free text) tied to ast-101.
  7. Re-computation — because the engines are "computed, not stored," the next call to computeGovernability() automatically reflects the new evidence — no code change required for this feedback loop.
  8. Audit and export — AuditLog records the sequence; if run inside a Workspace session, the existing Workspace Governance Export Pack could package the trail for delivery back to Javier.
Records created: one ReassessmentTrigger, one or more EvidenceRecords, one or more AuditLog/WorkspaceAuditEntry entries. No new tables, types, or engines are touched.

10 · Final Verdict

Executive Conclusion

1. What exactly is Javier asking for?
A single, bounded, real (not synthetic) test of whether OMG's governance context and Aegis's decisioning can meet at a genuine interface, using one real workflow pattern, with the resulting evidence returned to OMG.
2. What does OMG already have?
A real governed-asset registry, ownership/authority modeling, a working evidence-sufficiency engine, and a working admissibility engine that already composes evidence + authority + change signals into a bounded decision outcome — plus a separate, more elaborate (but disconnected) Change Request/Approval module.
3. What is missing?
Any entity for "consequential action with outcome," any external-system integration point, and a single unified change/material-change model — two incompatible GovernanceState vocabularies currently exist, serving two disconnected code paths.
4. What minimum information must be obtained?
One existing asset, a mapped material-change category with narrative, evidence artifacts, and Aegis's decision as free text (Section 5).
5. What should be requested from Javier?
Exactly the four items in Section 9.
6. What should NOT be requested from Javier?
Integration specifications, credentials, or a formal Aegis output schema — none of it can be consumed today.
7. Is a meaningful OMG ↔ Aegis evaluation achievable?
Yes — as a manual, one-shot, evidence-handoff exercise using existing OMG containers, not as a live or structured integration.
8. What is the recommended next step?
Run exactly one instance of the pattern using ast-101, capturing Aegis's output as a plain-text EvidenceRecord, and observe whether the existing Admissibility Engine's output changes in a way both sides find meaningful — before considering any development investment.
Final verdict: READY WITH DATA COLLECTION. OMG's governance engines are real and reusable today. Aegis's contribution has nowhere purpose-built to land — it lands as free text in a container designed for something else. That is sufficient for one bounded evaluation. It is not sufficient for a repeatable integration without development.
